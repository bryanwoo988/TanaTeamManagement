# Tana Team — 团队日历与发票 PWA 设计文档

日期：2026-11-15
状态：已批准（2026-11-15）

## 1. 这是什么，为什么要做

用户有一个农业 App，里面的日历用来安排农场工作，但目前每人只有自己的日历，没有团队、没有邀请。Tana Team 是一个**独立的 PWA**，补上这一块：

- 一个团队（例如一个农场）共用一份工作日历，大家看到同样的安排
- 员工拍收据报销，会计上传公司发票，管理员和会计能看到全部
- 可以导出 Excel / PDF，用手机分享出去
- **不做聊天**

使用者是几个人的小团队。工人多数只有手机号码，不一定有 Email。田里信号可能不好。

成功的样子：工人每天晚上收到“明天的工作”提醒，不用再打电话问；月底会计从 App 导出一份带收据照片的 PDF，就能做账。

## 2. 目标 / 非目标 / 反目标

**目标**
- 电话号码登录，一个人可属于多个团队，每个团队的角色不同
- 团队共享日历 + 个人日历，可叠加显示
- 公司发票与员工报销，带拍照
- 导出 Excel 和附照片的 PDF，并能直接分享
- App 内通知 + 手机推送
- 三语：华语 / English / Bahasa Melayu

**非目标（不做）**
- 聊天、留言、评论
- 多层审批（例如“主管先批准”）
- OCR 自动读取发票金额
- 自动重复的工作规则（例如“每两周施肥一次”）；改用“复制到其他日期”
- App 内付款

**反目标（就算功能能用，出现以下情况也算失败）**
- A 团队的人看到 B 团队的任何资料，或员工看到与自己无关的发票
- 通知太多，大家把通知关掉
- 收据照片丢失
- 短信被人刷光余额，导致登录验证码发不出去

## 3. 用户已决定的事

1. 独立的 PWA，不与现有农业 App 共用数据或代码
2. 后端用 **Firebase**，做法照用户的教会签到 App（`bryanwoo988/Church-attendance-`）
3. 电话号码 + 短信验证码登录，用 **Twilio Verify**，同一个 Twilio 账号，另建一个 Verify Service
4. 加入团队两种方式：**邀请码 + 管理员批准**，或**管理员用电话号码预先加入**
5. 一个人可以属于多个团队
6. 员工会上传收据报销；会计会上传公司发票
7. 会计上传公司发票时，通知管理员；员工是否收到通知，由会计在上传时勾选“相关的人”决定
8. 报销**不需要主管批准**，会计一人处理
9. 通知要有：明天的工作提醒、有新工作指派给我、会计上传了新发票（以及第 7 节的其余项目）
10. 推送用标准 Web Push，手机端做法沿用用户的 `CompareCast`，但发送放在 Firebase，不另开 Cloudflare
11. 三语
12. 外观：跟随手机 / 浅色 / 深色，加 4 种浅色主题和 4 种深色主题（照用户提供的参考图）
13. 登录页参考教会 App 的设计
14. 重复的工作用“复制到其他日期”处理
15. 被指派工作的通知一定要收到（不能关掉）
16. 不分期，一次做完

## 4. 技术路线

| 路线 | 取舍 | 结果 |
|---|---|---|
| **Firebase（React PWA + Auth + Firestore + Storage + Functions + Hosting）** | 用户已有一套跑通的 Firebase + Twilio 电话登录；Firestore 自带离线缓存；安全规则在服务器端执行；几个人用的费用接近零。缺点：复杂报表较难做；要 Blaze 方案（绑信用卡） | **采用** |
| Supabase | SQL 权限和报表较直观；但免费项目闲置会被暂停（几人用的 App 容易遇到），而且电话登录、部署都要从头做 | 不采用 |
| Cloudflare（Workers + D1 + R2） | 免费额度大、不用信用卡；但没有现成登录系统，权限要在每个 API 里自己写，也没有离线同步。这个 App 最怕的就是权限出错 | 不采用 |

推送另有一个选项：Firebase + Cloudflare Worker 专门发通知（照搬 CompareCast）。不采用，因为通知需要读取团队资料（谁负责哪项工作），Worker 必须拿 Firebase 管理员密钥，等于维护两个后端。

## 5. 角色与权限

角色跟着**团队**走，不跟着人走。同一个人可以在 A 团队是管理员、在 B 团队是员工。

| 角色 | 日历 | 发票 / 报销 | 团队管理 |
|---|---|---|---|
| 管理员 admin | 看全部；新增、编辑、指派任何工作 | 看全部；可上传公司发票；可处理报销；导出 | 批准申请、改角色、移除成员、重设邀请码 |
| 会计 finance | 同员工 | 看全部；上传公司发票；处理报销；导出 | ✗ |
| 员工 member | 看全部团队工作；新增工作（负责人只能是自己）；编辑指派给自己的工作 | 上传自己的报销；只看到自己上传的，以及会计勾选了自己的公司发票 | ✗ |

**规则**
- 只有 `active` 成员能看团队的任何资料；`pending` 只看得到“等待批准”
- 团队最后一位管理员不能退出，也不能把自己降级
- 成员被移除后，他上传过的报销和发票**留在团队里**（这是财务记录），他本人不能再看到
- 所有权限由 Firestore 和 Storage 的安全规则执行，不只是把按钮藏起来

## 6. 功能

### 6.1 登录
- 输入马来西亚电话号码 → 短信验证码 → 登入，之后一直保持登录
- 第一次登录时填名字
- 防刷：App Check、每个号码每天的验证码上限（默认 5 次，管理员不能改，写在后端设定里）、Twilio Verify 只允许发往马来西亚
- 可以更换电话号码（同样要验证码），做法照教会 App

### 6.2 团队
- 任何登录用户都能**建立团队**，建立者自动成为管理员，系统生成邀请码（短、好念，例如 `TANA-7K3P`，避开 0/O、1/I 等易混字符）
- **加入**：输入邀请码 → 状态 `pending` → 管理员批准 → `active`。管理员也可以拒绝
- 管理员可**重设邀请码**，旧码立即失效
- **用电话号码预先加入**：管理员输入电话号码、名字、角色 →
  - 这个号码已经注册过：直接成为该团队的 active 成员，并收到通知
  - 还没注册：先存成“预先加入”记录；对方第一次用这个号码登录时，自动成为 active 成员（不用邀请码、不用再批准）
  - 管理员可以在成员页看到“尚未登录”的预先加入名单，可以取消
  - 管理员填的名字先用来显示，对方登录后填了自己的名字，就以对方的为准
- 顶部有团队切换；“个人”也算一个选项

### 6.3 日历
- 一项工作的栏位：标题、日期、开始和结束时间（或“全天”）、负责人（可多人）、地点或区块（文字）、备注
- 视图：月视图、日视图（列表）
- 叠加显示：可以勾选个人日历和多个团队，用颜色区分
- 个人日历的工作只有本人看得到
- **复制到其他日期**：在一项工作上按“复制”→ 在日历上点选一个或多个日期 → 每个日期各建一份，标题、时间、负责人、地点、备注都一样。复制出来的每一份是独立的，改一份不影响其他份。负责人只收到一条合并的通知（例如“你被指派了 4 项新工作：11/18、11/20…”）
- 权限与新增工作相同：员工只能复制负责人是自己的工作
- 离线：看过的日历在没信号时也能看；离线新增或修改的，恢复网络后自动送出

### 6.4 发票与报销

两种类型：

| 类型 | 谁上传 | 状态 |
|---|---|---|
| 公司发票 | 会计、管理员 | 无状态，记录用 |
| 员工报销 | 任何 active 成员 | 待处理 → 已报销 / 退回 |

- 栏位：照片（必填）、金额（RM）、日期、商家、类别、备注；可选“相关工作”（连到一项团队日历工作）
- 公司发票另有“相关的人”（可多选），被勾选的员工能看到这张发票，也会收到通知
- 报销流程：会计按“已报销”（可填付款日期），或按“退回”（必须填原因）。被退回的报销，员工可以换照片或改资料后重新提交，回到“待处理”
- 类别清单：每个团队一份，由管理员维护，默认带几个农业常用类别
- 拍照：用手机相机或从相册选；上传前在手机上压缩（长边约 1600px，约 300–500 KB）
- 删除：员工只能删自己“待处理”或“退回”的报销；会计和管理员可以删任何一张

### 6.5 导出与分享
- **日历**：选团队和日期范围 → Excel 或 PDF。所有 active 成员可用
- **发票 / 报销**：选日期范围、类型、状态 → Excel（一行一张，含金额合计）或 PDF（摘要表加每张收据照片）。只有管理员和会计可用
- 生成后用手机的分享菜单（Web Share API）直接发到 WhatsApp 或 Email；不支持分享的浏览器就直接下载
- 不做公开的分享链接（避免财务资料外泄）

### 6.6 通知

两层：
1. **App 内通知**：铃铛加红点，加上通知列表。一定有，不依赖推送
2. **手机推送**：标准 Web Push（VAPID）。iPhone 要 iOS 16.4 以上，并且要先“添加到主屏幕”。设置页显示推送状态，并教 iPhone 用户怎么开

| # | 事件 | 通知谁 |
|---|---|---|
| 1 | 明天的工作提醒（每人每天一条汇总，没有工作就不发） | 负责人 |
| 2 | 有新工作指派给我 | 新被指派的人（自己指派给自己的不发） |
| 3 | 我的工作被改时间或取消 | 负责人 |
| 4 | 会计或管理员上传公司发票 | 该团队的管理员（上传者本人除外）和被勾选的员工 |
| 5 | 员工提交（或重新提交）报销 | 该团队的会计和管理员 |
| 6 | 报销已处理（已报销 / 退回） | 提交的员工 |
| 7 | 有人申请加入团队 | 该团队的管理员 |
| 8 | 申请已被批准 / 被管理员用电话号码加入团队 | 本人 |

- 每种通知可以自己开关，**但第 2、3 项（被指派工作、工作被改或取消）不能关掉**：设置页显示为固定开启
- 被指派的人如果还没开推送，App 每次打开都在顶部显示提示条，直到开启为止（iPhone 提示先添加到主屏幕）。推送无法百分之百保证送达（手机关机、没加到主屏幕等），所以 App 内通知一定同时存在
- 明天提醒的发送时间可以自己设定，默认 20:00。全 App 统一用马来西亚时间（Asia/Kuala_Lumpur）
- 一个人的每台手机都会收到；推送服务回报订阅失效（404 / 410）时，删除该订阅
- 明天提醒用去重记录，避免同一天发两次（CompareCast 的做法）

### 6.7 三语
- 华语、English、Bahasa Melayu，可随时切换；第一次打开时按手机语言自动选择
- 推送通知的文字用收件人自己选的语言
- 导出的 Excel / PDF 用导出者当下的语言

### 6.8 外观（模式 + 8 种主题）

参考图：`assets/appearance-reference.jpg`（用户提供）

- **模式**（分段按钮三选一）：跟随手机（默认）/ 浅色 / 深色。下方说明：“跟随手机时，手机是浅色就用你选的浅色主题，深色就用你选的深色主题。”
- **浅色主题**（四选一）：Classic、Paper、Mint、Lavender
- **深色主题**（四选一）：Midnight、OLED Black、Slate、Grape
- 每个主题用一个小预览方块展示：背景色、卡片、一条强调色、一条灰色文字线；选中的加强调色外框
- 浅色和深色主题**各自记住**，所以“跟随手机”能在两者之间自动切换
- 配色参考图片：Classic 中性白 + 棕色强调；Paper 米色纸感 + 橙棕强调；Mint 淡绿 + 墨绿强调；Lavender 淡紫 + 紫色强调；Midnight 深灰 + 金色强调；OLED Black 纯黑 + 金色强调；Slate 蓝灰 + 浅蓝强调；Grape 深紫 + 淡紫强调
- 设定存在这台手机上（不跟账号走），登录页也适用
- 主题名称三语都显示原英文名（是名称，不翻译）；其余文字照常翻译
- 颜色全部用 CSS 变量；8 种主题都要检查文字对比度（正文至少 4.5:1）
- 日历里多个团队的颜色在 8 种主题下都要分得清
- 导出的 PDF 一律用浅色

### 6.9 登录页
- 参考教会 App 的登录页（`src/auth/LoginPage.tsx`）：顶部渐变背景、App 名称、语言切换、输入电话 → 输入验证码两步、错误提示文字
- 换成 Tana Team 的名称、图标和配色；语言切换加上 Bahasa Melayu；加上浅色 / 深色支持（教会 App 只跟随手机设定）

## 7. 架构

```
手机（React PWA）
 ├─ Service Worker：缓存 App、接收推送（沿用 CompareCast sw.js 的处理）
 ├─ 拍照 → 压缩 → 上传
 └─ 生成 Excel / PDF → 分享
        │
Firebase
 ├─ Auth：Cloud Function 验证 Twilio 验证码后签发登录（custom token）
 ├─ Firestore：资料，加安全规则
 ├─ Storage：收据照片，规则读取 Firestore 的成员记录
 ├─ Functions：登录、团队、通知、定时提醒、清理
 └─ Hosting：网页
        │
Twilio Verify（短信）    Web Push 服务（Apple / Google）
```

### 7.1 资料结构（Firestore）

```
users/{uid}                          名字、电话、语言、通知设定、提醒时间
users/{uid}/events/{id}              个人日历工作
users/{uid}/notifications/{id}       App 内通知（类型、团队、对象、已读）
users/{uid}/pushSubs/{id}            推送订阅（每台手机一条）
users/{uid}/teams/{teamId}           我加入了哪些团队（方便列出，由后端维护）
teams/{teamId}                       团队名、建立者、类别清单
teams/{teamId}/members/{uid}         角色、状态（pending / active）、名字
teams/{teamId}/events/{id}           团队工作
teams/{teamId}/invoices/{id}         类型、金额（以仙为单位的整数）、日期、商家、类别、备注、
                                     照片路径、上传人、相关的人、相关工作、
                                     报销状态、付款日期、退回原因
inviteCodes/{code}                   邀请码 → teamId（客户端不能读）
phoneInvites/{teamId_e164}           预先加入：团队、电话、名字、角色、建立者（只有后端写；该团队管理员可读）
```

### 7.2 照片（Storage）

```
teams/{teamId}/invoices/{invoiceId}/{photoId}.jpg
```

读写规则与对应的发票资料相同。

### 7.3 Cloud Functions

| 函数 | 作用 |
|---|---|
| `requestLoginCode` / `verifyLoginCode` / 换号码 | 照搬教会 App |
| `createTeam` | 建团队、生成不重复的邀请码、建立者成为管理员 |
| `joinTeam` | 用邀请码申请加入 → pending |
| `resetInviteCode` | 管理员换邀请码 |
| `addMemberByPhone` / `cancelPhoneInvite` | 管理员用电话号码预先加入；取消 |
| 第一次登录时 | 查找这个号码的预先加入记录，自动加入对应的团队 |
| 资料变动触发 | 工作、发票、成员变动时，写入 App 内通知并发推送 |
| 定时任务（每 15 分钟） | 找出提醒时间落在这 15 分钟内的用户，汇总他明天的工作，发提醒 |
| 删除发票触发 | 连照片一起删除 |

批准成员、改角色、新增或编辑工作、上传发票、处理报销这些操作，由前端直接写入 Firestore，靠安全规则把关。

## 8. 分期

不分期，所有功能一次做完。实施计划内部仍按顺序搭建（地基 → 团队与权限 → 日历 → 通知 → 发票与报销 → 导出），每一步都有测试，但不分开上线。

## 9. 运维与费用

- 新建一个 Firebase 项目（不与教会 App 共用），Blaze 方案，设预算提醒（例如每月 USD 5）
- 区域：Functions 和 Firestore 用 `asia-southeast1`（与教会 App 一致）
- Storage 有 5 GB 免费额度（Firebase 官方价格页）。有第三方资料说只有美国区域的 bucket 能用免费额度，开工时再确认，再决定 bucket 放在哪里
- 短信：Twilio Verify 每次成功验证约 USD 0.05，另加发往马来西亚的短信费（普通 SMS 约 USD 0.26 一条，Verify 的实际单价以 Twilio 后台为准）。余额与教会 App 共用，**余额用完两边同时无法登录**，所以要开低余额提醒
- Web Push 免费
- 个人资料：遵守马来西亚 PDPA 2010
- 写一份 `docs/SETUP.md`，格式照教会 App

## 10. 设计者的判断（用户未明确决定，可推翻）

- 第三种语言是 **Bahasa Melayu**
- 外观设定存在本机，不跟账号走
- 默认主题：浅色 **Paper**、深色 **Midnight**（不默认 OLED Black：纯黑背景在部分 OLED 屏幕滚动时会有拖影，留给喜欢的人自己选）
- 员工能看到团队**全部**工作，但只能编辑指派给自己的
- 员工自己新增的工作，负责人只能是自己；指派给别人要由管理员来做
- 会计在日历上的权限与员工相同
- 成员被移除后，他的报销记录留在团队
- 明天提醒默认 20:00，没有工作就不发
- 不做公开分享链接
- 删除规则（见 6.4）
- 被退回的报销可以重新提交

## 11. 留给开发者决定

- 前端：Vite + React + TypeScript + `vite-plugin-pwa`；i18n 用简单字典（照教会 App）
- Excel 用 `exceljs`，PDF 用 `jsPDF` 或同类库，推送用 `web-push`
- 测试：Vitest（单元）、Firebase 模拟器（安全规则，重点测跨团队、跨角色不能越权）、Playwright（端到端）
- 照片压缩做法、日历组件、页面布局和视觉设计

## 12. 2026-11-15 修订（上线后）

起因：分配工作时成员手机收不到系统推送（App 内通知正常）；有成员找不到地方拍收据；管理员要能按人决定谁可以上传收据。

**A. 推送金钥只有一个来源 + 自我测试**
- 网页不再在打包时带 VAPID Public Key（取消 `VITE_VAPID_PUBLIC_KEY` 和 GitHub Secret `VAPID_PUBLIC_KEY`）。新 callable `getPushConfig`（需登录）从服务器密钥 `VAPID_PUBLIC_KEY` 回传 Public Key，网页每次打开取一次。这样网页订阅用的金钥永远和服务器签名用的同一对，不会因为手抄出错而被推送服务以 401/403 拒绝。
- 已有订阅如果是用别的金钥订的，算作“未开启”；开启时先退订再重订。App 启动时（已登录、有档案、通知权限已允许）若发现订阅金钥不对、或服务器已删除登记，会静默重新订阅并登记，失败只记 log。
- 设定 → 通知设定新增“发送测试通知”：callable `sendTestPush` 只推给自己的设备（用户语言），回报每部设备结果（只显示推送服务的主机名）；404/410 的登记照常删除；不写通知记录。

**B. 默认进入团队**：从未选择过范围（本机没有保存的选择）且只在一个团队是正式成员时，默认显示该团队（底部才有“发票”页）。明确选过的（包括“个人”）照旧。

**C. 按成员控制能否上传收据（默认可以）**
- 成员资料新增可选 `canUpload`（没有 = 可以），由触发器同步到 `users/{uid}/teams/{teamId}`。管理员/财务永远可以。
- 规则：新建报销（claim）和在新发票文件夹上传照片都要求有此权限；管理员可改**别人**的 `canUpload`（布尔值），任何人不能改自己的。被关掉的成员仍可修改/重交自己原有待处理或被退回的报销（包括补传照片）。
- 界面：成员页每位一般成员有“可以上传收据”开关（财务/管理员显示“总是可以”）。被关掉的成员在发票页仍看到“新增”按钮，但呈灰色不可按，旁边说明“管理员已关闭你的收据上传权限。”；底部“发票”页和历史记录照常可看。
